## .17 — Isolated migration acceptance

Run `cd deploy/shark-cloudflare && npm run release:migration-check`. The Python helper opens an **in-memory** SQLite database, reads only the repository's fixed `migrations/0001_public_only.sql`, rejects unexpected DDL, applies it locally twice to check idempotency, checks exact six research tables and `watch_due` index, foreign keys, integrity and the 288/day check. It returns a SHA-256 of the source SQL and marks `remoteMigrationApplied=false`.

**This command does not run Wrangler or authenticate to Cloudflare.** Keep the real D1 migration outside the workflow until separate owner consent, D1 ownership/empty-schema verification, and a backup/rollback decision. The independent D1 query preflight from LIVE.11 must still run first. Use a newly dedicated database, never a PupsonStuff/shared DB. Actual migration would constitute a remote persistence write and is NOT authorized by this source PR.

## .18 — Real CPU/provider benchmark acceptance harness (no network)

Prepare a **private, operator-transcribed** JSON file after an *independently authorized* representative Workers Free invocation using the exact deployed commit. The strict `--mode benchmark` checker requires: 40-character deployed SHA, UTC timestamp and evidence link, named source mode, invocation count, Worker **CPU** p50/p95/max (not elapsed wall time), wall p95, max subrequests, provider request/errors/rate-limiting and p95 provider latency, and D1 read/write counts. It rejects malformed/incoherent evidence and screens CPU max under 10 ms and subrequests under 50, zero provider rate-limit/error and at least 30 invocations.

The result always says `cloudflareCpuTelemetryVerified=false` and `cronAuthorized=false`, **even if numeric checks pass**. A human must independently inspect actual Cloudflare analytics, provider timestamps, workload completeness and shared quota headroom. Worker wall time includes I/O and is **not a CPU substitute**. A disabled Worker cannot yield representative public-market CPU measurements without a separately authorized, bounded, temporary sampling procedure. No sampling procedure or Cron is executed here.

Command: `python3 -B scripts/release_acceptance.py --mode benchmark --input /private/benchmark.json`. Never upload Cloudflare credentials or mint-level private evidence to public CI logs.

## .19 — Evidence-retention, budget and archival boundary

The `--mode retention` screen takes private owner-provided data: D1 database/account bytes, observed daily growth, active/open and retained cases, oldest unclosed age, and off-host restore status. It models **30 days of growth** against 80% of the nominal Free D1 500 MB/database and 5 GB/account ceilings, while preserving <=1000 active watches and identifying unclosed research over 36 hours. It never deletes or prunes rows; **past completed/censored cases and the at-most-once alert outbox remain evidence**. Missing/invalid numbers fail closed. A positive screen does not certify provider quota, billable status, stable 30-day growth or recovery.

Command: `python3 -B scripts/release_acceptance.py --mode retention --input /private/retention.json`. If limits are approached, stop discovery and obtain approval for a separately encrypted, complete archive and verified restoration. No automatic deletion or silent truncation.

## .20 — Local encrypted recovery drill and independent second-host requirement

The existing `scripts/export-encrypted.sh` requires a separate owner confirmation and Cloudflare auth to **read/export** a specific SHARK-only D1 to an age-encrypted local file; this sequence does not call it. The new **offline-only** `scripts/restore-encrypted-local.sh` takes:
1. An existing owner-held `.age` archive, 
2. A private **age identity file** available only on a trusted restore machine,
3. An expected 64-character SHA-256 of the encrypted archive from a separately recorded source, and
4. Optionally an expected JSON file containing `snapshotSha256` and per-table `counts` from a separately captured source receipt.

Example on a **second trusted machine** after manual transfer of only ciphertext (never upload identity/private keys):
```bash
export SHARK_CF_RESTORE_CONFIRM=ISOLATED-OFFLINE-SQL-RESTORE-ONLY
bash scripts/restore-encrypted-local.sh /private/archive.age /private/age-identity.txt \
  YOUR_RECORDED_64_CHAR_ARCHIVE_SHA256 /private/source-fingerprint.json
```

The script verifies ciphertext hash, decrypts to a private temp directory, invokes Python's isolated **in-memory** SQLite restore, checks exact SHARK schema, integrity, foreign keys, row counts and deterministic per-table fingerprint. A mismatched independently recorded expected fingerprint fails. The restored raw rows, ciphertext, identity and SQL are not printed. It unlinks temporary plaintext; this is **not guaranteed secure erasure on SSD**. SQL exports larger than 24 MB are deliberately refused by this initial memory-safe drill: certify a separate large-backup restore design before claiming larger data restoration. Optional Wrangler `d1_migrations` bookkeeping is allowed; other project tables fail.

Even a passing local drill reports `secondIndependentHostVerified=false` and `encryptedOffHostArchiveVerified=false`: a script cannot prove the host is independent, ciphertext actually crossed an owner-approved off-host boundary, identity separation, or revocation/corruption drills. The owner must record machine custody, source/cipher hash, separate off-host archive location, restored fingerprint and a human-attested restore result in [commissioning issue #1374](https://github.com/bookieandco/crispy-waddle/issues/1374), without secrets.
