## Code sequence

1. **OWNER.01 — Identity admission.** `personal-owner.ts` expresses the single permitted address and checks `id`, provider-backed `email_confirmed_at`, non-anonymous identity, and exact email. Email itself is not an entitlement or secret; no `user_metadata` authority is used. A fixed email is a policy selector rather than a substitute for ownership of the email inbox.
2. **OWNER.02 — First-use email verification.** Server action `sendOwnerSignInLink` sends a one-time Supabase Auth email on **explicit button click only** (`signInWithOtp`, owner-only, `shouldCreateUser:true`, email callback to `/settings/security`). This removes the requirement for a static enrollment password. Users must prove control of the inbox using Supabase's actual email verification; UI or code never self-confirms. Password/signup/recovery server actions also refuse other email addresses, with generic response for unrelated recovery addresses. Existing password enrollment remains as an optional fallback, not a forced second account.
3. **OWNER.03 — Protected admission.** Existing JWT claims are insufficient on private browser routes: middleware calls Supabase `getUser` for a live provider-confirmed identity and admits only the verified canonical email. Pre-existing independently bearer-authorized machine routes retain their separate controls. Public Auth callback remains reachable. Callback `verifyOtp/exchangeCodeForSession` checks owner before navigating and signs out wrong account. Password changes require the same verified owner check.
4. **OWNER.04 — Face ID passkeys.** Existing native Supabase WebAuthn register/signin code is reused (SDK `@supabase/supabase-js@2.116.0`, client experimental opt-in). Registration checks verified owner; sign-in checks verified owner and signs out a mismatched owner session. Normal passkey operation uses a new challenge/signature; it does **not** rotate a password, and device passcode/other authenticator fallback is possible. Face templates never leave the device.
5. **OWNER.05 — Regression and acceptance.** Unit tests exercise fixed email policy, valid/invalid/expired owner confirmation, test-account isolation, protected routes, passkey cancel/identity, and optional password recovery. CI + web build and actual iPhone enrollment are separate gates.
